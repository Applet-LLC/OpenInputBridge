# セキュリティ上の留意事項

このドキュメントは、OpenInputBridge(および同じInterceptionプロトコルを実装するドライバ全般)が
持つ、悪用され得る性質についての調査結果と、現時点での対応状況・未着手の検討事項をまとめたもの
です。2026年8月、商用版(Pro/Subscription)のEULA検討時の議論をきっかけに作成しました。

`docs/CLEAN_ROOM.md`(実装の出自の証跡)、`docs/PROTOCOL.md`(プロトコル仕様)とは目的が異なり、
こちらは「このドライバは技術的に何ができてしまうか」「それに対して何をした/何がまだ未着手か」を
継続的に記録するためのドキュメントです。

## 1. 未昇格プロセスからのシステム全体の入力監視・注入が可能

`driver/common/driver.c` のコントロールデバイス(`\\.\interceptionNN`)のACLは以下の通りです。

```c
static const WCHAR OibControlDeviceSddl[] = L"D:P(A;;GA;;;SY)(A;;GA;;;BA)(A;;GRGW;;;WD)";
```

`SY`(SYSTEM)・`BA`(Administrators)がフルアクセス、そして **`WD`(Everyone/全ユーザー)にも
汎用読み書き権限**が付与されています。これはコード中のコメントにもある通り、本家Interceptionの
ユーザーモードライブラリが `\\.\interceptionNN` を昇格なしの素の `GENERIC_READ` で開くという
既存仕様に合わせるための、意図的な互換性維持です(AutoHotkeyのInterception fork等、既存アプリを
無改変で動かすことが目的)。

結果として:

- ドライバの**インストール自体**には管理者権限(および商用版ではライセンス認証)が必要
- しかし**インストール後**は、管理者権限のない一般ユーザープロセスでも、プロトコルを知っていれば
  システム全体のキーボード/マウス入力を観測・注入できる

この性質は本家Interceptionと同一であり、OpenInputBridge固有の欠陥ではなく、プロトコル互換性を
維持する以上避けられない設計上のトレードオフです。

## 2. アンチチート等による検知可能性

技術的には検知され得ると考えるのが妥当です。

- カーネルレベルのアンチチート(EAC等)は自身もキーボード/マウスのデバイスクラススタックに
  フィルタとして常駐することが多く、`UpperFilters` レジストリ値や実際のフィルタチェーンを
  列挙・検査できる立場にある
- ロードされているカーネルドライバ(サービス一覧)の列挙、既知の署名・ハッシュとの照合、
  「見慣れない/未知の上位フィルタドライバがkbdclass/mouclassの直下にいる」こと自体を汎用的に
  検知するヒューリスティックも一般的
- 入力タイミングの統計的異常検知など、ドライバの種類に依存しない検知手法も併用され得る
- 本家Interceptionを使ったツールは、ゲーム業界のアンチチートコミュニティで既に広く認知・警戒
  されているカテゴリである。OpenInputBridgeは同一のワイヤープロトコル・デバイス命名
  (`\\.\interceptionNN`)を意図的に踏襲しているため、「Interceptionプロトコル利用」を検知する
  仕組みがあれば、OpenInputBridgeを使ったツールも同様に検知対象になり得る

**不確かな点**: EAC等の内部実装は非公開であり、「OpenInputBridge」という名前・サービス名・
カタログ固有のシグネチャで具体的に名指しされているかどうかは確認できていません。

## 3. 監視・キーロガー用途への転用リスク

- カーネルレベルのキーボード/マウスフィルタドライバによるキーロギングは、Interceptionの登場
  以前から存在する古典的な手法である
- 正規のリマップ/マクロツールと悪意あるキーロガーは、カーネル側では全く同じプリミティブ
  (入力の捕捉・改変・注入)を使っており、**両者を区別する要素はユーザーモード側コードの「意図」
  だけ**で、ドライバ自体に善悪の区別はない
- そのため、この種のドライバは一般に「二面性のあるツール」として認識されており、AV等が
  「監視ツール/PUA(potentially unwanted application)」カテゴリとしてヒューリスティック検知
  することも珍しくない

**不確かな点**: 「Interceptionが悪用された」と名指しされた具体的な公開インシデント・CVEを、
確証を持って提示できる情報は現時点で確認できていません。断定的な事例紹介は避けています。

## 4. 現時点での対応

- 商用版(Pro/Subscription)のEULA(`License.ja-JP.rtf`/`License.en-US.rtf`)に、不正アクセス・
  チート行為・無断監視目的での使用を禁止する条項を追加済み(2026年8月)。契約上の抑止力に留まり、
  技術的な防止策ではない点に注意
- 本README(`README.md`)に、利用規約上の注意喚起とこのドキュメントへの参照を追加済み
- **監査ログ・使用状況の可視化(SACL方式)、およびトースト通知**: デバイスドライバ本体
  (`driver/`)を一切改変せず、`\\.\interceptionNN`各コントロールデバイスにSACL(監査ACE)を
  付与し、Windows標準のオブジェクトアクセス監査(セキュリティイベントログ4656)で
  「どのプロセスがいつ開いたか」を記録する方式を採用することとし、2026年8月に設計を確定した。
  SACLはコントロールデバイス再作成のたび(=ドライバサービス起動のたび)に失われるため、
  タスクスケジューラのイベントトリガー式タスク(SCMのサービス開始イベントをトリガー)で
  再適用する。あわせて、該当イベントを検知した際に利用者へその場で知らせるトースト通知
  (専用AUMID `OpenInputBridge.AuditNotifier` 名義)も、ユーザーセッション内で実行される
  タスクスケジューラのタスクとして同様に実装する。実装はOSS版`installer/`に一本化し、
  Pro/Subscriptionの各インストーラーではオプション機能(Feature)として選択可能にする。
  検討の詳細・不採用とした代替案(DACL絞り込み・許可リスト・常駐サービス化・
  デバイスドライバ側への機能追加など)は`docs/DECISIONS.md`の
  「2026-08-08: 監査ログ(SACL)・トースト通知機能の設計」を参照

## 5. 検討が必要な対策案(未着手)

以下はまだ検討・実装していない候補であり、今後の課題として記録するもの。

- **DACLの絞り込み**: `Everyone` への読み書き権限を制限する案。ただし本家Interceptionプロトコル
  互換性(無昇格プロセスからの利用)とのトレードオフが大きく、単純な変更はできない
- **消費側プロセスの許可リスト/署名検証**: コントロールデバイスを開けるプロセスを制限する案。
  ただしプロトコル仕様自体には存在しない拡張であり、既存クライアントとの互換性を損なう可能性が
  高い
- **利用者への周知の強化**: 購入・インストール時点での明示的な同意取得(現状はEULA記載のみ)

これらは互換性・パフォーマンス・実装コストとのトレードオフが大きいため、着手する場合は個別に
`docs/DECISIONS.md` へ検討経緯を記録すること。
